# VU AI Academic Advisor — DATA308 Assignment #1

A RAG-based academic advisor for Vidyashilp University that answers student questions **only from the
university's own documents**, cites its sources, asks a clarifying question when it lacks facts about the
student, and says so when the documents don't contain the answer.

```
data/raw (4 university files) ─► extract_data.py ─► data/processed (md/json) ─► ingest.py ─► ChromaDB
                                                                                              │
Next.js chat UI ──► FastAPI /chat ──► advisor.py ──► retrieval (top-k + exact course lookup) ─┘
                                          │
                                          └─► prompts.py (4 strategies) ─► LLM chain (structured JSON) ─► UI
                                              Groq gpt-oss-120b → Groq gpt-oss-20b → Gemini flash-lite (fallbacks)
```

## Repository layout

| Path | What it is |
|---|---|
| `data/raw/` | The four files supplied with the assignment (handbook PDF, SOP PDF, semester-spread XLSX, minors XLSX). |
| `data/processed/` | Clean text/JSON extracted from the raw files (generated by `backend/extract_data.py`). |
| `data/synthetic/student_profiles.json` | 10 synthetic, anonymised student profiles (generated by `backend/make_profiles.py`). |
| `backend/` | FastAPI app, RAG pipeline, prompt strategies, LLM wrapper (Groq primary, Gemini fallback). |
| `frontend/` | Next.js 16 + TypeScript + Tailwind chat UI. |
| `eval/` | 25 test cases, the evaluation runner, results (`results.csv`, `summary.md`). |

## Run it locally

**Backend** (Python 3.11+):

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # then put GROQ_API_KEY and GEMINI_API_KEY in .env
python extract_data.py          # raw PDFs/XLSX -> data/processed   (already done; re-run if raw files change)
python make_profiles.py         # synthetic profiles                 (already done)
python ingest.py                # chunk + embed + store in ChromaDB (~30 s)
uvicorn main:app --reload --port 8000
```

**Frontend** (Node 20+):

```bash
cd frontend
cp .env.local.example .env.local   # NEXT_PUBLIC_API_URL=http://localhost:8000
npm install
npm run dev                         # http://localhost:3000
```

**Evaluation**: `LLM_PIN=groq:openai/gpt-oss-120b backend/.venv/bin/python eval/run_eval.py`
(25 cases × 4 strategies + 3 follow-ups; `LLM_PIN` forces one model for a fair comparison and waits out rate limits).
`--rescore` recomputes metrics from saved raw results without calling the API.

## API

- `GET /health` — status and model.
- `GET /students` — synthetic profiles for the dropdown.
- `POST /chat` — `{message, student_id?, strategy, conversation_history}` → structured JSON:
  `answer, confidence, grounded, sources[{source_file, section}], needs_clarification, clarifying_question,
  insufficient_information, conflict_detected` (+ `strategy, provider, response_time_s, retrieval_time_s, retrieved`).

## Latency design

- **Groq** (`openai/gpt-oss-120b`, reasoning effort `low`) answers in ~1-2 s; strict JSON-schema output means no
  re-parsing or retries.
- **Fallback chain** `gpt-oss-120b -> gpt-oss-20b -> gemini-flash-lite-latest -> gemini-3.5-flash-lite`, no SDK
  retries; a model that returns 429 is put on cool-down for its retry-after period and skipped instantly.
- **Retrieval** is local (MiniLM + ChromaDB, ~30-150 ms); the embedding model, ChromaDB and API clients are warmed
  up at server start.
- **Compact prompts**: profile rendered as one line per course, duplicate labels stripped, `max_tokens=1000`
  (Groq reserves max_tokens against its 8k tokens/minute free-tier budget).

## Prompt strategies (`backend/prompts.py`)

| Strategy | Adds |
|---|---|
| `baseline` | Raw question + generic instruction. No role, no documents, free text. |
| `structured` | Role/persona, explicit constraints, XML delimiters, JSON output with uncertainty flags. No documents. |
| `rag` | + top-k retrieved chunks with `[source_file | section]` labels, grounding & citation rules, conflict rule. |
| `rag_structured` | + the student's structured profile, current-term context, prerequisite-chain and own-semester lookups, and a step-by-step eligibility procedure with clarifying questions. |

## Simplifications / assumptions (state these honestly in the report)

1. **Current term is derived**, not given: the offering file is dated Sept 2026 and handbook clause 1.2 says the
   odd semester runs Jul/Aug–Dec, so the current term is taken as the odd semester (`data/processed/term_context.md`).
2. **Handbook Table 2 (letter grades)** is an image in the PDF; it was transcribed by hand into `handbook.md`.
3. **PDF/XLSX extraction is heuristic**: clause headings are detected by regex; the spreadsheet is read by fixed
   column positions. Pages of the handbook that are purely covers/contents/phone numbers were skipped.
4. **Student profiles are synthetic** (no real student data). Grades are invented; courses, credits and semesters
   come from the real semester spread, and credits/CGPA are computed with handbook clauses 8.11 and 8.16.
5. **Eval scoring is rule-based** (keyword + flag matching against verified expected outcomes). It can mis-label
   paraphrased answers; labels should be spot-checked. See the docstring of `eval/run_eval.py`.
6. **Free-tier rate limits**: Groq allows 8k tokens/min per model, so under load answers may come from the
   fallback model (the `provider` field says which). The evaluation is pinned to one model.
7. **Baseline cannot self-report** confidence/sources/flags — those fields are fixed defaults for it; the eval
   judges the baseline on the text of its answer.
8. `conflict_detected` was added to the brief's output schema so conflict handling can be measured directly.
9. Retrieval adds an exact course-code/title lookup on top of semantic search (MiniLM embeds codes like
   "DATA301" poorly).
